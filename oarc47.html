DNS OARC 47 Report
November 2026


Geoff Huston

DNS OARC held its 47th meeting in Vancouver in early November 2026. For those of us who seem to have fallen deeply into the DNS rabbit hole two full days of DNS topics is barely enough! In two packed days these meetings provide a concentrated overview on the current hot topics in today’s DNS. Here's a few highlights that I found to be of interest.

A Cuckoo Filter

A lot can be learned from analysing DNS traffic. Almost every network transaction starts with a call to the DNS to transform the name of a service into some form of network address. It’s a close to universal service and it's used for all kinds of purposes from service delivery in consumer environments through to orchestration of malicious botnet swarms, and everything in between. Little wonder that some see the DNS as a rich vein of information about network activity, while others see it as a control point, and others see it as the first line of defence in a hostile world. In the world of generating threat intelligence, the DNS is an essential input.

The key action here is to be able to gather and analyse the steam of queries: the names being queried, the resource records being sought, who is asking and when and where are they asking, and the answer they received. The larger the data set being analysed the better the analytic results that can be obtained, but at some stage the sheer size of the data feed presents a major challenge. The Quad9 open recursive resolver is by no means the largest recursive resolver service in today's Internet, but the data flows generated by its query streams are still impressively large, and the tools used to store and query this data set are becoming highly specialised.

Quad9's John Todd reported on their investigation of a "Cuckoo Filter" which appears to be a refinement of a Bloom Filter. Their aims here are include a need to keep data away from the core of their network, to use a data cache as a gatekeepers to slow floods and de-duplicate events, top still respond to queries in useful times, and in the process avoid impacting the network, the back-end store, or the budget! Cuckoo has the interesting property that it can respond with complete certainty when a queried name is known not in the stored set but is not no accurate if it responds positively that a name is in the stored set. The probability of false positive answers is a function of the selectable bit size of the fingerprint of the object, as the larger the fingerprint the lower the probability of these false positives. Quad9 are looking at further development of this approach, with functions such as a LRU storage regime with cache entry deletion and insertion, and a TTL on stored entries. The first reports for this tool are surprisingly efficient: 32 bits per object (1:70,000,000 false result), with some ~127 million objects at 95% capacity, a 30 day absolute TTL (14 bits), 3.5 days of LRU (10 bits), and a memory size of 1,073,741,824 bytes (1G) comes to a surprisingly small ~67 bits per object!


Figure 1 - Cuckoo Filters in the Quad9 processing pipeline (from presentation)

This tool opens some interesting analytic possibilities, including tracking newly observed domains, changes in name properties, name string similarities, and identification through name properties.

Chasing Milliseconds in DNS Resolution

There is a classic dilemma in DNS system design in large scale customer networks. The closer you can provision the resolver to the customer the lower the latency, but the smaller the cache hit rate as the resolver is serving a smaller population of end clients. A resolver positioned deeper in the network will have a higher query load and a better cache hit rate, but because its positioned deeper in common network infrastructure its likely to be further away and hence a higher latency.

The result of pushing the caches to closer to the edge is a compromise between latency and cache hit rates. Comcast are reporting a very respectable 10ms latency to reach the resolver cache, which for an extensive network is an impressive result in deployment engineering.

Cat and Mouse Resolution

DNS configurations lay a trail that resolvers necessarily must follow. The label sequence in a DNS name is one such trail. However, there are trails that are not so well ordered, including the alias records in CNAMES, and the resolution of nameservers into IP addresses when the glue records cannot be trusted or do not exist. These configuration structures cause the resolver to commence a new resolution task. Either accidently or deliberately such constructs can be used to cause a processing load on resolvers. The presentation by Cisco's DNS group shows 8 such examples where resolution has to undertake effort that ultimately can never lead to a completed resolution (Figure 2).


Figure 2 - DNS Loop Examples (from presentation)

Resolvers use a set of controls to defend their integrity. They often keep a record of the CNAMEs that have been encountered in a resolution task and call a halt as soon as a repeated name is encountered. They also keep a count of the number of CNAMEs in a resolution task and stop when an upper limit is reached. There is typically an overall time and work budget for each name resolution task and resolution is halted when the available budget is consumed. If a resolution task is terminated in this manner, then the original name is also cached for a small number of seconds by the resolver so that repetitions of this name resolution task can be immediately recognised and curtailed.

The conclusion from this presentation is that stopping a loop is not the same as stopping the cost imposed on the resolver, and stopping repeated work is more critical to overall resolver performance and capacity than detecting the loop.

Look, no NS!

It was reported earlier this year in a presentation by ISC's Ondrej Sury that the Bind recursive resolver has switched to a parent-centric delegation model. The nameserver delegation records in the DNS are part of the delegated (child) zone but are copied into the parent zone. A cautious resolver would follow one of these copied NS delegation records in the parent zone, as it has no choice, but would then retrieve the same NS records from the child zone as the authoritative record of the delegation. This change to the Bind code dispensed with these additional queries, as they appeared to offer no increment in benefit in any case. If the parent record was already corrupted in an effort to mislead the resolver, then the damage was already done when the record was retrieved and the retrieved values used to query the child zone. The query into the assumedly fake child record would presumably also give the same misleading NS records in any case.

So, while it is considered good DNS housekeeping for a child zone to contain nameserver resource records, it is pragmatically of no value these days (with a caveat we’ll consider). As Shane Kerr reported in a small experiment using a zone without NS records, none of the open recursive resolvers objected to the lack of a NS record in the child zone.

But this is not without an ongoing debate. There are currently two drafts on this practice in the IETF. One draft describes how recursive resolvers should adopt this parent-centric delegation model and the other draft describes delegation checking (termed "revalidation") using child zone data and proposes that a resolver that fetches these child zone records also validates them if the zone if DNSSEC-signed. I suspect that, as with many such debates relating to choices between correctness and rapid and efficient expedience, the expedient option generally becomes the default practice.

This highlights a deeper issue in the DNS about the nature of security protection offered by DNSSEC. Correctly configured, DNSSEC validation applied to a response from a signed zone ensures that the only names that are resolved and locally cached are resolved to a validated value. But that simply means that the answer is authentic. DNSSEC does not necessarily protect how that response was obtained, nor does it constrain the set or parties that may be queried while the resolver discovers the nameservers for the queried zone. The delegation data in parent centric resolvers is not DNSSEC-signed, and it is feasible for an on-the-wire interception attack, and DNSSEC does not require that these delegation referrals nor the IP addresses of nameservers be separately validated. DNSSEC validates the answer, not where and how you might have obtained the answer.

For a DNSSEC-signed zone, an interception attack cannot lead to a false answer being accepted (assuming that the keys have not been compromised), as this would not pass validation, but it can lead to queries being passed to third parties. The assertion that Wes Hardaker made in his presentation is that if we use with child-centric delegation, then the child zone's NS record is signed and can be directly validated, so that interception re-writing efforts of NS records can be detected. This is certainly true, but it is a major shift in DNSSEC validation practices. Such an additional measure would impose its own incremental costs in performing this validation of each child-zone signed delegation record. This leads also to consideration of the proposed DELEG record, which is proposed to be a signed parent-centric record.

It’s certainly possible to take a very cautious view of the DNS in an effort to minimise the exposure of an end user when making DNS queries, as well as minimising the risk of misdirection and third party inspection. Such a cautious approach would entail the use of oblivious DNS over HTTPS (RFC 9230), query name minimisation (RFC 9196) and perform DNSSEC validation of every delegation using the child-centric NS record, as well as using transport encryption to deflect efforts of on-the-wire interception.

Should a general use DNS resolver be designed to meet the most stringent of security standards under all circumstances? Or does the incremental cost in terms of additional processing and queries and delay make such an approach completely impractical in a standard retail ISP context (which is where the bulk of DNS resolution is performed in today's Internet). Can individual users opt out of a standard DNS offering and use a more stringently specified resolution environment? Even today the answer is “yes”, and users can define a custom DNS resolution environment that both obscures DNS queries from inspection and interception and validates all data before using it, though the effort to construct such a DNS resolution environment and conceal this traffic from various network firewalls and policy filters may be significant.

DNS Resolution Misbehaviour

We might prefer to deploy DNS name resolution systems that are efficient and fast, that doesn't necessarily mean that we get what we want! This APNIC Labs study looked at the number of queries received for a non-existent name, using their measurement platform to perform some 116M tests over a broad sampling of end users drawn from across the global Internet over a 7-day period in August 2026. The methodology included presenting each user with a unique DNS name to resolve, so that DNS resolver caching behaviour was deliberately bypassed. The result of these 116M tests was a total of 513M queries received by the authoritative nameservers, or an average of 4.43 queries per unique name. This is a repetition of a similar experiment undertaken in 2019, when the query multiplication factor was 2.37.

The causes for this increased query load can be traced to a strict limit in the DNS to only ask for one resource record type per query, so if an application wants to learn the IPv4 and IPv6 address records for the named resource then that's 2 queries to be performed back-to-back. Additionally, we’ve introduced the HTTPS service records, which can provide the service's preferred application access protocol.

The use of these additional query types still does not explain all of the increase in query volume, and in particular the increase in duplicate queries that are received within the first 10ms of the initial query. One plausible explanation is the widespread use of DNS load balancers in the large-scale ISP industry, and some observed propensity for these front-end systems to err on the side of query duplication in an effort to minimise the delay impact of query/response drop within the backend server set.

What is perhaps less obvious is that among the 5 different ways to respond negatively to a query, the level of query duplication varies considerably. Returning the code SERVFAIL is about as bad as simply refusing to respond at all! The conventional NXDOMAIN response is more efficient than answering positively. (Details are shown in Figure 3)

Quantum Computing and DNSSEC

While it has been known for many years that quantum computers could break so-called classical encryption algorithms in a faction of the time needed for conventional computers, there was always the comforting assessment that the engineering required to create a large-scale quantum computer with millions, or even billions, of qbits that could be held stable for more than a few fractions of a second was some decades away. But that comforting belief appears to have been undermined in recent months. While facts are scant, there is an increasing view from quantum pundits that it’s time to take the use of post-quantum cryptography in DNS far more seriously than we have in the past.

For encryption purposes where there is a requirement for integrity of the encrypted data for many decades to come, then the time to take post-quantum cryptography seriously has already some. For digital signatures there is an appreciation that it’s also time to move.

The core cryptography standards, ML-KEM, MK-DSA and SLH-DSA, appear to be settled, and ML-KEN is enabled by default across major browsers, OS TLS libraries and other encryption-sensitive applications.

In the world of DNSSEC there is much in the way of uncertainty about this potential shift into a world of port-quantum cryptography. A presentation by Cloudflare's Vicky Shrestha made the assertion that "we are hostages in a siege of response size paranoia". Or to put it another way from Verisign’s Matt Thomas, “The DNS has always been shaped by what fits in a packet.” UDP could carry this payload, but IP fragmentation is unreliable. TCP could carry this payload but there are impediments that cast a similar pall of unreliability, as well as an overhead in maintaining a TCP state on authoritative servers. In another quote from the same Cloudflare presentation: "This is why people joke about replacing the DNS protocol altogether, but they have a haunted look in their eye while they are choking back their tears."

Early measurement efforts to assess the viability of using ML-DSA 44 (algorithm 18) point to some widespread evidence of breakage, so it’s reasonable to expect that the initial steps along the post-quantum path will be somewhat tentative, and the initial models will be likely to be opt-in some form.

OpenSSL may have already introduced native support for ML-DSA-44 as of version 3.5, but that is just part of the initial steps only a longer journey. Work is needed on standardised DNS specifications, DNS provisioning protocol specifications, as well signing and validation tools. We need to review the capability to support TCP everywhere in the DNS, as well as being capable of accepting large payloads in both servers and resolvers. We need to understand the impact of widespread use of stateful TCP sessions in the DNS, particularly in the resolver to server connections, and the interaction of the interpretation of the DO bit in the context of a TCP response.

When considering TCP and scale there is also the consideration of the proliferation of front-end load balancing systems to spread a large query load across a local farm of systems, whether they are recursive resolvers or authoritative servers. If the resolver client keeps the TCP session open, which would be a natural behaviour in order to defray the session setup cost against multiple queries, then the front end has limited ability to re-route this session to a different back-end server. TLS and QUIC sessions are potentially harder to switch between back-end servers. This factor may cause unexpected transient bottlenecks in the server environment. There is also a behaviour difference between TCP and UDP. When a server reaches its TCP limit no new connections are accepted, while the loading under UDP relates to simpler individual packet loss.

When we blithely observe: "Well, it’s just going to be DNS over TCP, and we already know how to support that." I suspect its glossing over some aspects of the way we manage the DNS query load which will not map cleanly into TCP. Supporting TCP when TCP is used for less than 1% of queries is markedly different to a proposition where TCP would be used for every query with the DO bit set, which today approaches some 60% of queries.

Counting the use of NSEC and NSEC3 in the DNS

I must admit to a significant level of personal bias when reviewing DNS measurement presentations when we are looking at the measured properties of DNS zones, such as this presentation that looks at the use of various forms of negation in DNSSEC. A small number of names and zones are used by billions of Internet users continually (think of the name “google.com”) while the long tail is used at a significantly lower level of query intensity. Calculating averages across this highly skewed profile can often generate misleading conclusions.

There appears to be a basic technology choice in serving a DNSSEC-signed zone, and the potential to have hybrid approaches that lie somewhere between these two choices. One approach is to preprocess a complete zone file and add signature records in this preprocessing phase, and then serve the zone, with its signatures, in a conventional manner. The other basic choice is to attach a signature record as the final processing step of generating a response. For positive responses there is little semantic difference between these two basic choices, but for negative responses there are some major differences. In a pre-signing mode, the signer does not know in advance the query name that does not exist, so it can only answer in terms of the names that are defined in the zone. The NSEC record is used to sign the span between two "adjacent" names in a zone and thereby claim in a verifiable manner that all names that fall between these two names do not exist. The NSEC3 approach is a minor variation that obscures the order of names in the zone to prevent zone enumeration, but it’s essentially the same approach. When using a dynamic signer, the signer has access to the query name, and the signer can construct a signed response that can specifically assert that the queried name does not exist.

It’s a little deeper than that, and the NSEC and NSEC3 records can be used in aggressive NSEC caching to enrol recursive resolvers in the role of defending authoritative servers against random name attacks, as the cached NSEC(3) records can answer all queries that fall within the defined name span of the record. Dynamic signing using Compact Denial records, or NODATA with NXNAME, cannot use the same level of assistance from recursive resolvers and the random name attacks generate additional passes through the crytpo signer for every query. There are also considerations of using multiple providers to serve a signed zone which is a lot more straightforward with a pre-signed zone, which there are additional considerations to address when signing a zone with multiple ZSKS in a multi-dynamic signer mode.

What that implies is that the choice of which signing design, and which negative response technology to use depends on the specific circumstances of the zone. Accordingly, I find the metrics and averages in this presentation extremely challenging to put into a useful and informative context.

Recursive to Authoritative DNS channel encryption

The effort to encrypt all DNS communications appeared to founder once the work on stub-to-recursive channel encryption. The IETF specified DNS over TLS (RFC 7858, RFC 8310), DNS over HTTPS (RFC 8484) and DNS over QUIC (RFC 9250) in short order. Normally, the overheads of setting up the encrypted channel would present a prohibitive barrier to an application which appears to be addicted to a lightweight UDP stateless packet exchange, but in the context of the stub-to-recursive scenario the initial connection overhead can be amortised over the subsequent queries. The use of a streaming protocol that does not exhibit head of line blocking, such as DNS over QUIC and DNS over HTTPS/3 (which uses QUIC) can be efficient as UDP with the same non-blocking properties.

The recursive to authoritative channel is different. There is no end user IP address in these DNS queries so the privacy issues are not as acute. A recursive to authoritative data channel would not normally be persistent, so the overheads of channel setup, as compared to the query and response transaction, would be an issue here. Also, if the channel capabilities of the server were not known in advance, then the resolver client would need to detect these capabilities by probing, which would take more time.

If we want to signal the capabilities of the server then there are a number of ways to achieve this. One way is by using the proposed DELEG record where the capabilities of the server are contained in the delegation record in the parent zone. Another approach is to associate the transport capabilities of the server in a service binding transport hint associated with the server’s name and use the record as an opportunistic additional inserted record in the Additional section of a response.

I must admit that this opportunistic approach to transport signalling seems a whole lot more sensible to me. It does not entail a massive change to one of the fundamental properties of the DNS, delegation, and it can be adopted incrementally. This seems like a vey precise solution to a precisely bounded problem!

Presentation

Stop ANY

The DNS is a one trick pony: you send a query and you get a response. That’s it. No ping. No control channel. None of that. You just send a query and you get an answer. However, there is one special query type: ANY.

It had been assumed that ANY was analogous to a mythical ALL query type, returning all defined RRsets for a given query name. Indeed, it was sometimes used as a single query replacement for querying for A and AAAA RRsets. However, the same ANY query has been used in DNS amplification attacks using spoofed source addresses and UDP transport, as the query is generally far smaller than the response. This attack vector has led to some servers returning a minimal response to ANY queries (RFC 8482). This RFC proposed that DNS responders could opt to send a smaller response than the complete collection of RRsets for a name, and suggested three possible responses, where it could just respond with a subset or even just one RRset for the name, or return a synthetic record, the HINFO record, or try to guess what records the requestor wanted and respond accordingly.

There is an attractive alternative: to simply decline to respond to an ANY query using a NOTIMPL (not implemented) response code, which is what is being proposed in an internet draft.
